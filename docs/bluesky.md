# SOTD × Bluesky

**Status: proposal. Nothing here is built.** No file in this repo talks to
Bluesky today. This document is the design sketch and the reading list —
if you're a future session, don't assume any of it exists.

The idea: give the Song of the Day journal a comment section, an audience,
and a permanent public address, without adding a backend, a database, a
build step, or a bill.

## Why Bluesky specifically

Bluesky the app runs on **AT Protocol**, which splits a social network into
four swappable pieces:

- **PDS (Personal Data Server)** — holds a user's repo: a signed,
  Merkle-tree'd collection of JSON records. Every record has an
  `at://did:plc:xyz/collection.name/rkey` URI. You own the repo and can
  host it yourself; by default it lives on `bsky.social`.
- **Lexicon** — the schema language. `app.bsky.feed.post` is one lexicon
  among infinite; anyone can define their own (`solutions.deets.sotd.entry`
  would be a legitimate record type), and custom records federate like
  everything else.
- **Relay / firehose** — aggregates every repo's commits into one event
  stream. **Jetstream** is the friendly version: plain JSON over WebSocket,
  filterable by collection, no CBOR/CAR decoding.
- **AppView** — indexes the firehose into a product. Bluesky's is
  `public.api.bsky.app`.

The operative fact for this site:

```
$ curl -sD - -o /dev/null -H "Origin: https://deets.solutions" \
    "https://public.api.bsky.app/xrpc/app.bsky.actor.getProfile?actor=bsky.app"
HTTP/1.1 200 OK
Access-Control-Allow-Origin: *
```

**The public AppView's read endpoints are unauthenticated and CORS-open.**
A browser can call them directly — no key, no proxy, no worker. That is the
whole reason this is cheap, and it's the opposite of the League tab, where
every Riot call has to squeeze through a rate-limited worker
([docs/league.md](league.md)). Verified 2026-08-03; if it ever stops being
true, this design needs a worker and stops being cheap.

## Three phases

Each is independently useful and independently abandonable. Do them in
order; stop whenever it stops being fun.

### Phase A — identity

A DNS TXT record at `_atproto.deets.solutions` containing `did=did:plc:...`
makes the Bluesky handle `@deets.solutions`. DNS is already at Cloudflare;
this is one record in a dashboard already in use. Nothing in the repo
changes.

Free, reversible, and worth having on its own even if B and C never happen.

### Phase B — publish

A **new, separate** `scripts/post-sotd.ps1`. Separate is the whole point —
see "The unattended-publish line" below.

For each song not yet posted: `com.atproto.repo.createRecord` with an
`app.bsky.embed.external` — track and artist as the text, the song's
`artwork_url` as the embed thumb, and a link back to the site. Auth is an
**app password** (free, revocable, scoped — never the account password),
stored in `scripts/secrets/` alongside what's already there.

The response carries the new record's `uri`. That's the value Phase C needs.

### Phase C — read

**The join must not touch `songs.json`.** That file is generated by the
sibling [DeetsOTD](https://github.com/deets-137/DeetsOTD) repo and is
read-only by convention ([docs/data.md](data.md)) — the next
`scan.py --enrich --web` would erase any field injected into it.

So the poster owns a sidecar instead:

```
sotd/bluesky.json   →  { "11393": "at://did:plc:xyz/app.bsky.feed.post/3k2...", ... }
```

Keyed on `post_id`, which is already stable and unique per song.
`songs.json` stays pristine and regenerable, the sidecar is independently
rebuildable, and neither generator needs to know the other exists.
`sotd.js` loads both and joins them.

Rendering: when a song card is expanded, fetch

```
https://public.api.bsky.app/xrpc/app.bsky.feed.getPostThread?uri=<at-uri>
```

and render the replies plus the like/repost counts under the card.

**Lazily — on expand only, never 350 fetches on page load.** That's the one
hard performance constraint in the design.

## Costs

**Cloudflare Pages: zero impact.** No build step, no new dependency, no
worker, no D1. The site stays flat files served as they are today. Added
bytes: one small JSON — ~350 entries is roughly 30 KB if backfilled, and
one line a day going forward.

**Bluesky: $0.** No API key, no billing relationship, no signup beyond an
account.

Rate limits, and whose they are:

| | limit | our usage |
|---|---|---|
| Writes | 5,000 points/hour, 35,000/day; CREATE = 3 points (≈1,666 creates/hour) | 3 points/day |
| Reads (public AppView) | undocumented, "generous" | per **visitor** IP, not ours |

That second row is the good part: read load scales with traffic without
ever concentrating on a key we own.

The real costs are the non-monetary ones:

- **Moderation.** Replies are public Bluesky content appearing under a song
  on this site. Decide up front whether the thread renders raw or filtered
  (follows-only is the usual cheap answer). This is the question that
  should actually decide whether B+C happens.
- **Graceful degradation.** A deleted post 404s. The card must shrug and
  render nothing rather than break.
- **Surface area.** One more script, one more secret, one more thing that
  can quietly stop working.

**Lock-in is low.** The identity is a `did:plc:` that survives changing both
PDS and handle, the records are exportable, and deleting `sotd/bluesky.json`
returns the site to exactly what it is today.

## The unattended-publish line

`scripts/nightly-sotd.ps1` has a deliberate safety property, stated in its
own header: it commits but **never pushes**, so a bad pull can't reach the
live site unattended.

Posting to Bluesky *is* publishing to the world, with no review step and no
clean undo. Folding the poster into the nightly job would quietly discard
the exact property that job was built around.

So the rhythm stays the one that already exists: nightly refreshes
`songs.json` and commits; you glance; then you run `post-sotd.ps1`, which
posts what's new, writes the sidecar, and pushes. Manual gate preserved.

## Ideas deliberately not taken

- **SOTD as a custom lexicon** — publish each song as a
  `solutions.deets.sotd.song` record in our own PDS repo, making the journal
  portable, addressable data anyone could consume off the firehose. Very
  on-brand, genuinely elegant, and *expression rather than utility*: nothing
  would consume it but us.
- **A feed generator.** A feed returning only our own posts is trivial (an
  HTTP endpoint returning a list of URIs — a Worker does it in ~30 lines).
  A feed that indexes *other people's* posts needs a persistent firehose
  consumer, which Workers are bad at: a Durable Object nursing a WebSocket
  with alarm-based restarts, and still fragile. Don't.
- **Bluesky OAuth as a second sign-in**, letting visitors reply as
  themselves from the page rather than on Bluesky
  ([docs/accounts.md](accounts.md) already does Google). AT Proto OAuth uses
  DPoP + PKCE and is meaningfully harder than Google's flow. Later, if ever.

## Reading

In the order worth reading it:

1. [AT Protocol Glossary](https://atproto.com/guides/glossary) — ten minutes;
   gets PDS / relay / AppView / DID straight so nothing else confuses.
2. [ATProto for distributed systems engineers](https://atproto.com/articles/atproto-for-distsys-engineers)
   — the best single explanation of *why* it's built this way. Read this one
   properly.
3. [Bluesky API docs](https://docs.bsky.app/) — the HTTP reference. This
   design needs exactly two endpoints: `com.atproto.repo.createRecord` and
   `app.bsky.feed.getPostThread`.
4. [Rate limits](https://docs.bsky.app/docs/advanced-guides/rate-limits) —
   short; worth skimming so the table above is yours, not inherited.
5. [Lexicon spec](https://atproto.com/specs/lexicon) — only if the custom
   record type above still tempts.
6. [Jetstream](https://github.com/bluesky-social/jetstream) and the
   [feed generator starter kit](https://github.com/bluesky-social/feed-generator)
   — bookmark, don't read yet.
